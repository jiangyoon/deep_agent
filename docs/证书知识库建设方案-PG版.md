# 证书知识库建设方案（PostgreSQL 版）

> 证书知识问答智能体语料建设与检索系统的完整方案（定稿）。覆盖：库架构、43 份政策文件入库清单、PostgreSQL 与 Milvus 定稿数据结构、灌库流程、四条查询链路、执行顺序与验收。
>
> 定稿时间：2026-11-18。**重建落盘 2026-11-19**（原云端稿未提交 git，按会话决策记录重建，数据现状均以实库核实为准）。
> 关系库已由达梦 DM8 迁移至 PostgreSQL 系（ArteryBase）：库 `career`，表名 `kb1_*` 小写蛇形；达梦版方案不再维护。

**需求背景：** 员工关于证书政策、职称申报条件、证书奖励及报销流程的咨询量大且重复率高。证书政策分外部（各省不一、定期更新）与内部（散落多份文件）两类；每位员工实际情况（学历、专业、已有证书、社保）不同，通用宣贯无法覆盖个性化问题。目标：构建证书知识问答智能体，实现政策问答 + "千人千路"个性化推荐。

## 一、总体架构与库划分

### 1.1 双库分工

| 库 | 存什么 | 干什么 | 现状 |
|---|---|---|---|
| **PostgreSQL**（`career`） | 政策原文（sections）、文件来源与时效（sources）、附件挂接（attachments）、证书↔职称对应（mappings）、奖励目录（rewards + shared_rules）、年度时间表（schedules）、申报条件规则矩阵（rule_channel_requirement）、证书别名（aliases）、问题台账（issues） | **单一事实源**：原文、状态、结构化规则全在这里；换版、标注修正只改这一处 | 已就绪 |
| **Milvus**（`career_policy_sections`） | 每条款一条记录：section_id、检索文本、稠密向量、稀疏向量、source_id | **语义召回**：员工用大白话提问（问法不含原文词）时靠向量命中条款 | 408 条已灌，Qwen3-VL-Embedding-8B |

**分工边界一句话**：Milvus 只管"问得模糊也能召回"，所有判定、过滤、溯源、版本、状态都在 PG；Milvus 不存任何需要维护的语义字段（渠道/地区/时效一律不冗余进向量库，避免标注一改就要重灌）。

### 1.2 配合链路

```
员工提问
  ├─ ① 意图路由（LLM 三分类：政策问答 / 证书精确 / 千人千路）
  ├─ ② 政策问答：PG 取"现行有效"白名单 source_id → Milvus expr `source_id in [...]` 预过滤 → dense+BM25 混合检索 → 回查 PG sections 原文 → LLM 组装（带文号溯源 + 附件下载链接）
  ├─ ③ 证书精确：别名解析 → PG kb1_mappings（对应职称）/ kb1_rewards（奖励金额）直接 SQL，不走向量
  └─ ④ 千人千路：员工画像 × kb1_rule_channel_requirement 精确匹配 → 给出可走路径与差额年限
```

### 1.3 规则表的定位（必要性结论）

规则矩阵不是技术必要，是**质量保证**：向量检索只能回答"政策怎么写"，"我行不行"需要拿画像做条件判断与年限计算，语义检索算不了。纯 RAG 的致命弱点是召回失败静默——LLM 不会说"没查到专科条款"，会基于残缺上下文自信作答。规则表把高频判定从"看模型发挥"变成"查表必对"。

投入策略：**只做高频可核对项**（内部认定/评审 + 集团高工 + 北京 AI，共 32 行，约 2 人天）；业绩、破格条件留原文（`extra_raw`）不进判定字段；全通道矩阵、iHR 对接、推荐引擎单独立项，按真实咨询数据决定。

### 2.7 清洗六步（每份文件通用）

1. 格式转换与解析（docx/pdf/xlsx → 文本 + 表格 + 定位信息）
2. 去重（内容级 SHA256 + 载体级人工比对）
3. 表格抽取（政策条件表 → 结构化；空白表单 → 附件区）
4. 多栏/乱码修复（多栏 PDF 按栏位重排；字体乱码按原图视觉转录）
5. 元数据标注（文号、层级、渠道 route、地区 region、适用年度、时效 validity_status）
6. 双轨产出（切块入向量库 + 可核对条件抽入规则矩阵）

### 3.3 数据治理约定

- 码值列全部加 CHECK 约束（validity_status / embedding_status / route / source_kind / rewards.grade）
- 换版：新版新增 source 行 + replaces_source_id；旧条款、旧附件仍指旧行；切换时同时启用新版、停用旧版

- 台账：issues 表带 status/resolved_at/resolution，问题可追溯

## 四、Milvus 定稿结构

### 4.1 Collection：`career_policy_sections`

| 字段 | 类型 | 说明 |
|---|---|---|
| `section_id` | VARCHAR PK | 显式主键 = PG sections.id，upsert 幂等 |
| `search_text` | VARCHAR | 章节标题 + 正文（**灌库时动态拼接**，不在 PG 落副本） |
| `dense_vector` | FLOAT_VECTOR | **Qwen/Qwen3-VL-Embedding-8B（上下文 32K），整条不切段**（最长正文 2,224 字符，远在限内） |
| `sparse_vector` | SPARSE_FLOAT_VECTOR | BM25 自动生成（中文分词），支撑文号/证书名等精确关键词 |
| `source_id` | VARCHAR | 与 PG sections.source_id 恒等；检索预过滤锚点 |

索引：dense HNSW（COSINE）+ sparse 倒排；标量 `source_id` 建索引供 `in [...]` 预过滤。

### 4.2 灌库流程

1. 从 PG 直读 `kb1_sections`（embedding_status='待入库'），拼 `chapter + heading + text` 为 search_text
2. Qwen3-VL-Embedding-8B 生成稠密向量 → 写入 Milvus（section_id 主键，重试幂等）
3. BM25 自动生成稀疏向量
4. 回写 `embedding_status='已入库'`、`embedding_model`、`indexed_at`
5. **换模型必须全量重灌**（向量空间与维度都变）；查询侧 embedding 必须与灌库同模型

### 4.3 检索约定

- **白名单**：先查 PG `validity_status='现行有效'` 的 source_id 列表 → Milvus `expr: source_id in [...]`；白名单为空不检索
- 混合检索：dense + BM25 → 融合重排（RRF 或 rerank 模型）
- 命中后回 PG 取 section 全文 + source 标题/文号 + 附件列表

### 4.4 四条查询链路

**① 政策问答**：白名单 → 混合检索 → 回查原文 → LLM 组装（引用文号 + 附件下载链接）。

**② 文号点名**（"182 号对破格怎么规定"）：`doc_no` 等值命中 → 未命中查 `doc_no_aliases` → 简写"182号"先出候选，重号按年份/发文单位消歧 → 命中印发通知时沿 `kb1_attachments` 导航到制度正文（N003→N001 已实存）→ 仅在该 source_id 内混合检索。**PG B-tree 不支持 LIKE 前缀通配走索引**（pg_trgm 为可选模糊方案）。

**③ 证书精确查询**（"一建对应什么职称/奖励多少"）：不走向量检索。
- 别名解析（kb1_certificate_aliases，18 条，已逐行验命中）→ LIKE 匹配
- 对应职称查 `kb1_mappings`（record_status 默认 review_ready）；奖励查 `kb1_rewards` + `kb1_shared_rules`（按 source_id 查目录说明）
- **双来源分流**：北京口径 → N017（对应表文件）；集团口径 → N035（高工条件附表）；渠道未明确 → 合并展示相同对应结果，标明两份依据与条件差别（N017 带"本市"限定、N035 不带）
